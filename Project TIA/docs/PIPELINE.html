TIA pipeline, step by step

What happens to one change, from the moment someone presses Run analysis to the stored report. Click a step in the pipeline (or use the ← → keys) to see what goes in, exactly how the step works, and what comes out.

Running example: a developer removes the field disputed from the Payment response of payments-service (branch contract, compared with main). Two other services, statement-service and customer-portal, call that API.

Steps are in the order the code runs them.

1. Request

Someone asks "what does this change affect?". The request is checked before any work starts.

Goes in

A web click, a REST call (POST /api/v1/impact-analyses), or a pull-request webhook from GitHub, GitLab, Bitbucket or Azure DevOps.

Comes out

An authenticated request, tied to exactly one tenant (customer), with a target repository, a head (branch, commit or PR number) and an optional base.

How it works

  1. Classify the route. Every route must appear in a permission table. A route with no entry is refused (403), so a forgotten endpoint is closed, not open. This one needs the analyze permission.
  2. Check the caller. Rate limit, then the tenant gate: is this tenant active, and is there storage room?
  3. Bind the tenant. The database transaction runs set_config('tia.tenant_id', …). PostgreSQL row-level security then hides every other tenant's rows. A transaction bound to no tenant sees nothing.
  4. Check repository access. A repository the caller may not read answers 404, exactly as if it did not exist.
  5. Choose the door. By default the analysis runs in the request. With ?async=true, or for a webhook, it is queued and a worker runs the same code.

The webhook door

  • The webhook signature is verified and the repository matched before anything is queued.
  • The job is keyed by provider, repository, PR number, head commit and base, so a re-delivered webhook is the same job.
  • Jobs of the same pull request share a group: a newer push marks older queued jobs superseded and asks a running one to cancel.

In the example

POST /api/v1/impact-analyses
{"target": "payments-service", "head": "contract", "base": "main"}

Code: api.py, authapi.py, rbac.py, gate.py, db.py (Database.tx), jobs.py (enqueue), webhooks.py

2. Resolve

Branch names move. This step replaces every name with an exact commit id, so the analysis can be repeated later and give the same answer.

Goes in

Target repository, head (branch, commit or PR number), base, optional limits.

Comes out

A concrete request: base commit, head commit, the list of repositories in scope with a commit for each, the limits, and the tenant configuration it runs under.

How it works

  1. Head. A PR number is fetched from the host; a branch or commit is resolved in TIA's own clone.
  2. Base. The base is the merge base of the base branch and the head: the commit where the branch started. Changes other people merged into main since then are not counted as this developer's change.
  3. Scope. Every registered repository of the tenant, unless the request names a smaller set. The target is always included.
  4. Other repositories. Each is resolved to a commit (its default branch unless a revision is given). With more than four, this runs in parallel threads because each costs a git process.
  5. Limits are ceilings. max_depth = min(requested, tenant maximum), and the same for max_results. A caller can ask for less, never for more.
  6. Identity. A hash of target, base, head, scope, revisions, limits and configuration is the job key. The same concrete request is the same job.

In the example

 "base": "80d082d…", "head": "482b101…",
 "scope": ["customer-portal", "payments-service", "statement-service"],
 "revisions": {"customer-portal": "…", "statement-service": "…"},

3. Read git

TIA asks git three questions: which files exist at this commit, what is in them, and which files differ between base and head.

Goes in

A local clone of each repository and the commit ids from step 2.

Comes out

For each commit, a map of file path → blob id. For the target, the list of changed files. File contents on demand.

How it works

FunctionGit commandReturns
resolve_revreads .git/HEAD and refs/heads/… directly; falls back to git rev-parsea 40-character commit id
list_treegit ls-tree -r -zpath → blob id, regular files only (symlinks and submodules skipped)
read_blobsone git cat-file --batch for many filesblob id → bytes
changed_filesgit diff --name-status --no-renameslist of (status, path)

Two properties that the rest depends on

  • The blob id is the content's identity. Two files with the same bytes have the same blob id. Step 4 uses it as the cache key.
  • Code is only read. Nothing is imported, built or executed. A hostile repository cannot run anything inside TIA.

In the example

4. Extract

Each source file is parsed into facts. The target repository is extracted twice (base and head); every other repository once.

Goes in

A repository, a commit, its file tree and the bytes of files not seen before.

Comes out

One RepoExtract per repository and commit: lists of endpoints, schemas, functions, call sites, tests, entities, migrations, UI pages, written test cases, and the files that failed.

How the caching works

  1. Whole-commit cache. If this repository at this commit was extracted before (same extractor version, same settings), the stored RepoExtract is returned and nothing below runs.
  2. Read the small files first. tia-services.yaml, Spring config and contracts/*.json give the service name, owner, criticality and which config keys point at which service.
  3. Choose the files. Files a parser exists for, minus the tenant's exclude patterns.
  4. Build one key per file: 
    repo | service | strip_prefixes | exclude_patterns | EXTRACTOR_VERSION | blob id | path
    Upgrading any parser changes EXTRACTOR_VERSION, so old facts cannot survive an upgrade.
  5. One query asks the store which keys it already has. Only the missing files are read and parsed.
  6. Assemble. Per-file facts are joined into one RepoExtract. Things that need the whole repository are resolved here (for example a Java class inheriting fields, or an ORM entity's table name). A full rescan uses the same assemble function, so incremental and full results are equal.

Path normalisation

Every path is normalised so both sides of a call can meet: {account_id}, ${id}, <id> and :id all become {}, fixed segments are lower-cased, the query string and trailing slash are dropped, and the tenant's gateway prefixes are stripped.

/accounts/{account_id}/payments      →  /accounts/{}/payments      (provider's route)
f"…/accounts/{account_id}/payments"  →  /accounts/{}/payments      (consumer's call)

Parsers by language

  • Python: the standard ast module (FastAPI, Flask, Django REST).
  • Java: tree-sitter (Spring Boot, OpenFeign, JPA).
  • C#, Go, Kotlin, TypeScript/JavaScript: tree-sitter adapters behind an adapter registry.
  • OpenAPI files, SQL and stored procedures, Kafka producers and consumers, ORM models: their own adapters.
When a file cannot be parsed (syntax error, not valid UTF-8) it is added to files_failed with the error. It later appears under Unknowns and makes the report partial. It is never silently skipped.

5. Diff

The target's base facts are compared with its head facts. TIA does not diff text lines; it diffs the facts from step 4.

Goes in

The target's RepoExtract at base and at head, plus git's list of changed files.

Comes out

Raw change records: contract changes, event changes, data changes, procedure changes, changed and added functions, configuration changes, and leftover files.

How it works

  1. Protect against unreadable files. Any file that fails to parse at head is removed from the base side too. Otherwise every endpoint and function in it would look deleted, and every consumer would be reported broken. The count of declarations left out is reported as an unknown.
  2. Contracts (diff_contracts). For each base endpoint, find the head endpoint with the same method and normalised path.
    • Not found, but the same handler now serves another route → endpoint_method_or_path_changed.
    • Not found at all → endpoint_removed.
    • Found → compare response shape (object vs list), success status, authentication markers, and each parameter (newly required, allowed values removed, constraints tightened).
    Then for each base schema: removed, each field removed, field type changed, field became required, enum values added or removed, constraints tightened, field added.
  3. Events (diff_events). Topics and message schemas, the same way.
  4. Data (diff_data). Migrations added between base and head, and the table and column operations they declare (dropped, renamed, type changed, made required, added).
  5. Stored procedures, views, triggers. Compared by a digest of the definition, then by signature: added, removed, signature changed, or body changed (with which tables it now writes or no longer writes).
  6. Functions. Match by id. A base function missing at head is removed; one whose hash differs is modified; an id only at head is added.
  7. Configuration (configkeys.analyse). Keys whose value was added, removed or changed in .env, properties, YAML, INI, TOML or settings JSON files; and keys that code starts or stops reading. Values are never recorded, only that they changed.
  8. Leftovers. A changed file that none of the above explains, and that is not a test or a .md/.txt file, becomes a file-level change.

 "seeds": ["payments-service:schema:Payment"], "used_by_endpoint": true}

6. Classify

Each raw change is given an effect, and turned into a seed: a starting point in the graph with a kind. Classification happens at three levels.

Goes in

The raw change records from step 5 and the tenant's compatibility rules.

Comes out

changed_components (what the report lists), seeds (what the walk starts from), and one overall change_type.

Level 1: is a contract change breaking?

ChangeBreaking?
Endpoint removed; method or path changedAlways
Response field removedYes, if the schema is returned by an endpoint
Field type changed; schema removedYes, if the schema is used by any endpoint
Request field became required, or a new required request fieldAlways
Field added (optional, or on a response)No: compatible
Request enum value removed; response enum value added; request constraint tightened; parameter now required; response shape changed; success status changed; authentication added or changedYes by default. Each is a named rule the tenant can reconfigure.
Authentication removedNot breaking for consumers; flagged for security review
Headers, error response bodiesNot evaluated. Reported as "compatibility not evaluated", never as compatible.

Level 2: what is the effect of a changed function? (classify_function)

The checks run in this order; the first that applies decides.

#CheckEffect
1The function is gone, something at head still calls that name, and no function with that name remainsbreaking
2The function is gone and nothing calls itcompatible_change
3body_hash is equal (only the docstring differs)no_functional_change
4The signature changed incompatibly and at least one caller in the repository was not changedbreaking
5The signature changed incompatibly and every caller was updated in the same changebehaviour_change
6Anything else: the body changedbehaviour_change

What counts as an incompatible signature change:

  • Python: a parameter removed, a parameter that lost its default, a new parameter without a default, positional order changed, return type changed. Parameter names matter because callers may pass them by keyword.
  • Java: the list of parameter types changed, or the return type changed. Names do not matter to callers.
  • A new parameter with a default is compatible.

A data seed also carries an access mode. A new required column only breaks code that inserts, so its seed is marked write and the walk follows only write edges from it.

The overall change type

The first match wins: test_only (every changed file is a test) → no_functional_change → api_change → event_change → data_change → config_or_file_change → implementation_change.

7. Build graph

All extracts are joined into one typed graph. The target contributes its base facts: the graph describes the landscape as it is today, and the change is then walked through it.

Goes in

One RepoExtract per repository in scope.

Comes out

A Graph: nodes with a type, edges with a relationship, an evidence status, a strategy and the file and line that prove them. Plus a list of calls that could not be resolved.

How it works

  1. Reuse if possible. The graph id is a hash of its inputs (each repository's commit, extractor version, configuration version, prefixes, schema version). If a graph with that id is stored, it is loaded and steps 2–8 are skipped.
  2. Nodes. One per service, function, type, schema, endpoint, call site and test.
  3. Endpoint edges. service EXPOSES endpoint; handler function HANDLES endpoint; endpoint USES_SCHEMA schema.
  4. Call edges inside a repository. Calls are matched by function name.
    • Exactly one function has that name → a confirmed CALLS edge.
    • Several have it → one inferred edge to each candidate (rule INF-CALL-AMBIGUOUS), so the call is not lost but is never presented as certain.
  5. Inheritance. INHERITS edges between types, with the same one-or-many rule.
  6. Test edges (static association, the test is not run):
    • the test's HTTP call matches an endpoint's method and path → confirmed, strategy test-http-call;
    • the test imports a module and calls one of its functions → confirmed, test-import-call;
    • only the file name matches (test_x.py ↔ x.py) → inferred, INF-TEST-NAMING.
  7. Events. Topic nodes; PUBLISHES from producers; listener nodes with CONSUMES_EVENT.
  8. Cross-repository edges are added by step 8. Then the data layer (entity MAPS_TO table, function READS/WRITES), SQL lineage, and the use-case structure (screens, elements, locators, request and response fields, rules).

How the graph answers "who is affected?"

Every edge is stored in the direction a change travels. The direction per relationship is fixed in one place, the graph schema.

Edge as writtenA change travelsMeaning
A CALLS BB → Achanging the callee affects the caller
call site CONSUMES_API endpointendpoint → call sitechanging the provider affects the consumer
endpoint USES_SCHEMA schemaschema → endpointchanging a schema affects the endpoints that use it
function HANDLES endpointfunction → endpointchanging the handler affects its endpoint
function READS/WRITES tabletable → functionchanging data affects the code that uses it
EXPOSES, HAS_SCREEN, HAS_ELEMENT, …not traversedstructure the tester views read; never changes an impact result

8. Link services

The hardest part: deciding that a call in one repository reaches an endpoint in another. This is the only place a cross-repository relationship is created, and matching names alone never creates one.

Goes in

Every call site, every endpoint, every declared contract, and the merged service map (which config key, host or client package belongs to which service).

Comes out

CONSUMES_API edges with a strategy and evidence status; an unresolved list with a reason for each call that got no edge; resolution statistics.

How one call site is resolved

  1. R1, generated or shared client. The call goes through a client package. Look the package up in the service map. If exactly one of that provider's handlers has the called method's name → edge, source_confirmed.
  2. R2, fully resolved HTTP call. The call has a path and a known base.
    • Base is a config key → look the key up in the service map.
    • Base is a host → look the host up, or accept it if it is itself a service name.
    • Among that provider's endpoints, exactly one matches the normalised path and the method → edge, source_confirmed.
    • Several match → no edge; reason "call matches N endpoints".
    • None match → no edge; reason "no endpoint … found in provider".
  3. R5, unique path match. Only if there is still no edge and the call is not through a client package. If exactly one endpoint in all other services has this method and path → edge, but marked inferred with rule INF-PATH-UNIQUE. Not used when R2 already named a provider and found no such endpoint there.
  4. Otherwise unresolved. The call goes on the list with its reason.

Then the declared contracts (R3)

  • Each interaction in a contracts/*.json file is matched to exactly one endpoint of the named provider.
  • If the same consumer already has a code-level edge to that endpoint, that edge is upgraded to corroborated (strategy R2+R3).
  • If not, a contract_ref node is created with a contract_confirmed edge.

Evidence statuses, strongest first

9. Walk

Starting from each seed, TIA follows the graph outward to everything that depends on it. This is a breadth-first search with explicit limits.

Goes in

The graph, the seeds (those whose node exists in the graph), and the limits: depth 8, 200 results, 60 seconds by default.

Comes out

reached: for every affected node, the path from the seed, the edges on that path, and which seeds reach it. Plus a truncated flag with the reason.

How it works

  1. Add runtime callers first. Callers seen only in ingested production traffic are added to this analysis's own copy of the graph.
  2. Pass 1: confirmed edges only. For each seed, take a queue starting at the seed. Repeatedly take a node and look at impacted_by(node), in sorted order so the result is the same every time.
  3. Rules applied at every step:
    • If the path already has max_depth edges, stop here. If the node still had dependents, mark the walk truncated.
    • A test node is an answer, not a road: it is recorded but never walked through.
    • An inferred edge is skipped in this pass.
    • A seed marked write follows only WRITES edges to data; one marked read only READS.
    • If the time budget is used up, or max_results nodes are reached, stop and mark truncated.
  4. First path wins. The first time a node is reached, its path is stored. If another seed reaches it later, only that seed's number is added.
  5. Pass 2: inferred edges allowed. Runs only if pass 1 was not truncated. Because first path wins, anything reachable through confirmed evidence keeps its confirmed path; pass 2 only adds what could not be reached otherwise.
When a limit is hit the report says which one, lists it under Unknowns, and its status becomes partial. Raising max_depth in the tenant configuration lets the walk go further.

10. Findings

Not every reached node is worth reporting. This step decides which ones become findings, what kind of impact each is, and writes the explanation.

Goes in

reached, the seeds, the graph, the head extract of the target.

Comes out

A list of findings, each with component, impact type, change nature, evidence status, path, reason, tests, limitations and required verification. No severity yet.

Which node becomes which finding

Reached nodeImpact type

How one finding is filled in

  1. Change nature. breaking if any seed that reaches the node is breaking; else nonbreaking; else unclassified.
  2. Evidence status of the path: the weakest link. Checked in this order: any stale edge → stale; any inferred edge → inferred; any runtime-only edge → runtime_observed; then corroborated, contract_confirmed, and only if every edge is from source, source_confirmed.
  3. Reason. A sentence built from the node type and resolution strategy, ending in "Change: …". For example "depends on the changed provider through a fully resolved HTTP call at file:line".
  4. Tests. Tests whose own path passes through this node and ends in a TESTS edge.
  5. Limitations. Added when the relationship is inferred or stale, the change was only analysed at file level, no test evidence was found, or criticality is not configured.
  6. Required verification. "Run: test names", or "identify and run consumer tests" when none were found, and "verify compatibility with the deployed consumer version" for other repositories.

Data findings (entities)

  • Lists the functions that read or write the entity.
  • A new required column produces no finding for a service that never writes to the table.
  • Checks whether the head revision already updated the mapping (fixed_in_head): if the same change drops the column and removes it from the entity, the finding is low.
  • Services in other repositories are linked only if they declare the same database.

Stale relationships

A consumer whose file can no longer be read is not in the graph, but may still depend on the changed endpoint. Such previously confirmed relationships get a finding marked stale, with "re-scan and confirm" as the verification, instead of disappearing.

11. Score

Severity is one small, pure function. The same four inputs always give the same severity, and every finding records the rule that produced it.

Goes in

For each finding: change nature, evidence status, whether it is in another repository, and the affected service's criticality.

Comes out

Severity, the rule id, whether the finding is material, and the final order and ids (F1, F2, …).

After scoring

  1. Tenant overrides. A tenant may set a different severity for a rule. The finding then records the rule, the default and the configured value, and the report lists the override under Unknowns. Overrides are never silent.
  2. Material? Yes if the severity is critical, high or medium, or if there is a breaking change on the path. Thresholds are tenant settings.
  3. Sort and number. By severity (highest first), then depth, component, node. The sort makes the order identical on every run. Then ids F1, F2, … are assigned.

In the example

Breaking + another repository + confirmed + not critical → row 4: high, SEV-BREAKING-CONFIRMED. The demo reports 5 high findings.

Import a catalog marking statement-service critical and run it again: its two findings match row 3 and become critical (SEV-BREAKING-CRITICAL); the others stay high.

12. Tester views

Findings are written for engineers. This step re-expresses the same result as things a tester can act on without reading code.

Goes in

reached, the seeds, the graph, every extract (including written test cases and UI pages).

Comes out

test_scope: entry points to test, rule gaps, consistency checks, configuration checks, and the regression selection.

Entry points (test_scope)

  • Reached nodes are projected onto entry points: API endpoints, in the changed service and in every service that calls it.
  • Each gets a plain name if its owners declared one under entry_points: in tia-services.yaml ("Monthly statement PDF").
  • Each gets a why (the chain of code from the change to it), a change effect (the strongest on its path) and the tests found.
  • Reached code that no analysed endpoint calls is listed separately, not dropped.

Rule gaps (rule_gaps)

  1. Take an endpoint that two or more services consume.
  2. For each consumer, collect the business rules (item filters from step 4) on the code path that handles the response.
  3. Keep only rules that test a field of the endpoint's declared response schema.
  4. If one consumer applies a rule and another does not, report it: the rule, where it is applied (function, file, line) and where it is missing.

Configuration checks

  • A key changed in a config file: which entry points read it.
  • Code newly reads a key: which file sets it, or "no file in the repository sets it, set it in the environment before testing".

Regression selection (regression.select)

Every written test case lands in exactly one list.

  1. Find what the case tests. Endpoints it names (the Entry point column, or a route or plain name in its text), plus endpoints called by any page it names.
  2. Names a page that calls no API → not affected, with that reason.
  3. Names nothing TIA can match → could not be mapped, review by hand. Never treated as unaffected.
  4. None of its endpoints were reached → not affected by this change.
  5. At least one was reached → run again, with a reason per reached entry point (its change effect and why).
  6. Sort the selected cases by effect strength, then by the case's priority.
  7. Cases the change itself added or edited are listed apart: they are new tests, not regression.
What "run again" means: the change reaches what the case tests. It does not mean the case will fail. Matching is static and textual.

In the example

entry points:  Payments screen · Monthly statement PDF · GET /accounts/{account_id}/payments
               all "breaking", 4 linked tests

rule gap:      shared endpoint  GET /accounts/{account_id}/payments
               rule             not p['disputed']
               applied by       statement_rows (statement-service, line 10)
               missing in       Payments screen (customer-portal)

14. Enrich

The static result is complete. This step adds what other systems have told TIA, evaluates the tenant's release policy, and removes anything secret.

Goes in

The report so far, and evidence that pipelines pushed in earlier: test runs, coverage, runtime calls, deployments, builds, incidents, approvals.

Comes out

The final report dictionary.

How it works

  1. Structural context. Circular dependencies, highly connected files, upward calls across folder layers, and groups of files that call each other, for the changed repository. Plus a Mermaid diagram of the services involved. This is derived context: it never adds or removes a finding.
  2. Test evidence. Each linked test gets its last CI result: passed, failed or no_ci_results. Without ingested results, tests are listed as "associated", not as passed.
  3. Runtime. Findings whose relationship was also seen in production traffic are marked.
  4. Deployments and builds. Which revision of each affected service runs in which environment, and whether the proposed revision has been built.
  5. Failure signatures. Recurring test failures across the history, and incidents carrying the same signature.
  6. Owners. The owning team of each affected service, from the tenant registry or tia-services.yaml.
  7. Release policy. The tenant's rules are evaluated on the report: pass, fail, requires_review or not_evaluated. By default the mode is advisory.
  8. Scrub. The whole report passes through scrub_json. Anything that looks like a credential is removed, counted, and reported as "treat as exposed and rotate".
Evidence is never fetched during an analysis. Only records already ingested are used, and their ids are pinned in the snapshot. That is what keeps the result reproducible: ingest first, then analyse.

After the demo's seed script has pushed evidence, a fifth consumer appears: mobile-app, known only from runtime traffic, with the limitation "outside the analysed repositories". test_portal_payments shows no_ci_results if no test run was ingested for its repository.

15. Store

The report is saved together with a record of exactly what it was computed from, and an entry in a tamper-evident log.

Goes in

The final report and every input identity: commits, parser versions, graph id, configuration, evidence ids.

Comes out

Rows in analyses, evidence_snapshots and audit_log, all owned by the tenant.

How it works

  1. Snapshot id. A hash over each repository's commit and extractor version, the head commit, the graph id, the stale relationships, each repository's scan state, the ingested evidence ids and the configuration identity: 
    snapshot_id = "snap-" + sha256(repr((snap_src, cfg.ident(CONFIG_VERSION))))[:12]
  2. Analysis id. For a pull request: tia-pr-<number>-<head commit>. Otherwise a hash of target, base, head and snapshot id. The same inputs give the same id.
  3. Store the snapshot with the full configuration settings, limits and evidence ids, then store the report.
  4. Audit entry. Appended to a hash chain: 
    hash = HMAC-SHA256(audit_key, prev_hash | seq | ts | event | payload)
    Each entry includes the previous entry's hash, so editing or deleting a row breaks the chain from that point. The key is kept outside the database, so someone who can edit rows cannot recompute a valid chain.
  5. Pin the commits. Every analysed commit is kept reachable in TIA's clones so the analysis can be reproduced after branches move or are deleted.

Reproducing a report

POST /api/v1/impact-analyses/{id}/reproduce re-runs steps 3–14 on the pinned commits, configuration and evidence, without storing anything, and compares the two reports. It answers {"identical": true, "versions_match": true}, or lists the differences. If a pinned commit is no longer available it refuses instead of answering from something else.

In the example

GET /api/v1/audit/verify   →  {"ok": true, …}

Rules applied before anything is shown

  • Redaction. Findings, tests, paths and regression reasons in repositories the reader cannot access are removed, and the report says how many were omitted.
  • Newest wins. A newer push to the same pull request sets cancel_requested on the running job. The worker checks that flag before it starts and again just before it writes to the pull request, so a slow old analysis does not overwrite a newer result.
  • Advisory. By default TIA never blocks a merge.
